### 1.2 技术选型建议

| 层级 | 推荐技术 | 备选方案 | 选择理由 |
|------|---------|---------|---------|
| **前端** | React 18 + TypeScript | Vue 3 + TS | React生态成熟，组件库丰富，TypeScript强类型安全 |
| **UI框架** | Tailwind CSS + Headless UI | Ant Design | 轻量、定制性强、响应式友好 |
| **后端** | Node.js (Express/NestJS) | Python (FastAPI) | 前后端统一TS生态，开发效率高；Python备选用于AI/ML重度场景 |
| **数据库** | PostgreSQL + Redis | SQLite(初期) | PG支持JSON字段适合卡牌数据；Redis缓存热点查询 |
| **AI服务** | Kimi API (视觉+文本) | 多模型fallback | 团队已有Kimi使用经验，视觉模型支持截图识别 |
| **文件存储** | 本地存储 / 云OSS | - | MVP阶段本地即可，用户量增长后迁移OSS |
| **部署** | Vercel / 自有服务器 | Cloudflare Pages | 快速部署、自动CDN、Serverless友好 |
| **截图识别** | Kimi vision model + 自研OCR后处理 | Azure Vision / Google Vision | Kimi API已集成视觉能力，中文场景表现好 |

## 二、数据架构

### 2.1 卡牌数据库设计

**核心表：`cards`**

```sql
CREATE TABLE cards (
    id              SERIAL PRIMARY KEY,
    game_version    VARCHAR(10) NOT NULL,        -- 'sts1' | 'sts2'
    character       VARCHAR(30) NOT NULL,        -- 'ironclad' | 'silent' | 'defect' | 'watcher' | 'necrobinder' | 'regent'
    name_cn         VARCHAR(50) NOT NULL,        -- 中文名
    name_en         VARCHAR(50) NOT NULL,        -- 英文名
    cost            INT,                         -- 费用（-1=X费，-2=无费用限制）
    type            VARCHAR(20) NOT NULL,        -- 'attack' | 'skill' | 'power' | 'curse' | 'status'
    rarity          VARCHAR(20) NOT NULL,        -- 'basic' | 'common' | 'uncommon' | 'rare' | 'special'
    effect_base     TEXT NOT NULL,               -- 基础效果描述
    effect_upgraded TEXT,                        -- 升级后效果描述
    keywords        TEXT[],                      -- 标签数组：['exhaust', 'ethereal', 'retain', ...]
    image_url       VARCHAR(255),               -- 卡牌图片URL
    
    -- 元数据
    created_at      TIMESTAMP DEFAULT NOW(),
    updated_at      TIMESTAMP DEFAULT NOW(),
    patch_version   VARCHAR(20),                -- 最后更新版本
    
    -- 约束
    UNIQUE(game_version, character, name_en)
);

-- 索引
CREATE INDEX idx_cards_game ON cards(game_version);
CREATE INDEX idx_cards_character ON cards(character);
CREATE INDEX idx_cards_type ON cards(type);
CREATE INDEX idx_cards_rarity ON cards(rarity);
CREATE INDEX idx_cards_keywords ON cards USING GIN(keywords);
```

**搜索辅助表：`cards_search`**

```sql
-- 用于全文搜索
CREATE TABLE cards_search AS
SELECT id, game_version, character, name_cn, name_en,
       setweight(to_tsvector('simple', coalesce(name_cn, '')), 'A') ||
       setweight(to_tsvector('simple', coalesce(name_en, '')), 'A') ||
       setweight(to_tsvector('simple', coalesce(effect_base, '')), 'B') ||
       setweight(to_tsvector('simple', coalesce(effect_upgraded, '')), 'B')
       AS search_vector
FROM cards;

CREATE INDEX idx_cards_search ON cards_search USING GIN(search_vector);
```

### 2.4 流派数据库设计（知识图谱型）

```sql
CREATE TABLE archetypes (
    id              SERIAL PRIMARY KEY,
    game_version    VARCHAR(10) NOT NULL,
    character       VARCHAR(30) NOT NULL,
    name_cn         VARCHAR(50) NOT NULL,        -- e.g., "力量战", "防战", "毒贼"
    name_en         VARCHAR(50),
    difficulty      VARCHAR(10),                 -- 'easy' | 'medium' | 'hard' | 'combo'
    description     TEXT,                        -- 流派说明
    
    -- 核心牌（JSON数组）
    core_cards      JSONB NOT NULL,              -- [{"card_name": "...", "quantity": 2, "upgraded": true}, ...]
    
    -- 可选/辅助牌
    support_cards   JSONB,
    
    -- 关键遗物
    key_relics      JSONB,
    
    -- 禁止/冲突牌
    avoid_cards     JSONB,
    
    -- 策略说明
    early_game      TEXT,                        -- 前期策略
    mid_game        TEXT,                        -- 中期策略
    late_game       TEXT,                        -- 后期/BOSS策略
    
    created_at      TIMESTAMP DEFAULT NOW(),
    updated_at      TIMESTAMP DEFAULT NOW()
);

-- 卡牌-流派关联表（方便反向查询：一张牌属于哪些流派）
CREATE TABLE card_archetype_links (
    card_id         INT REFERENCES cards(id),
    archetype_id    INT REFERENCES archetypes(id),
    role            VARCHAR(20) NOT NULL,        -- 'core' | 'support' | 'optional'
    PRIMARY KEY (card_id, archetype_id)
);
```

### 2.5 用户与对局记录

```sql
CREATE TABLE users (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    device_id       VARCHAR(100),               -- 匿名用户标识
    email           VARCHAR(100),               -- 可选登录
    created_at      TIMESTAMP DEFAULT NOW(),
    last_active     TIMESTAMP DEFAULT NOW(),
    daily_quota     INT DEFAULT 10,             -- 每日AI问答次数（匿名）
    plan            VARCHAR(20) DEFAULT 'free'   -- 'free' | 'premium'
);

CREATE TABLE game_sessions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id         UUID REFERENCES users(id),
    game_version    VARCHAR(10) NOT NULL,
    character       VARCHAR(30) NOT NULL,
    ascension       INT DEFAULT 0,              -- 进阶等级
    seed            VARCHAR(50),                -- 游戏种子（如玩家提供）
    outcome         VARCHAR(20),                -- 'win' | 'lose' | 'abandoned' | 'in_progress'
    final_floor     INT,
    
    created_at      TIMESTAMP DEFAULT NOW(),
    ended_at        TIMESTAMP,
    
    -- 统计快照
    stats_summary   JSONB                       -- 抓取卡牌数、击杀数、最终血量等
);

CREATE TABLE session_screenshots (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_id      UUID REFERENCES game_sessions(id),
    timestamp       TIMESTAMP DEFAULT NOW(),
    floor           INT,                        -- 当前层数
    phase           VARCHAR(30),                -- 'combat' | 'card_reward' | 'map' | 'event' | 'shop' | 'rest'
    
    image_path      VARCHAR(500),               -- 存储路径
    image_hash      VARCHAR(64),                -- 去重/缓存
    
    -- AI识别结果缓存
    ocr_result      JSONB,                      -- 识别出的卡牌、能量、敌人等
    player_notes    TEXT,                       -- 用户手动备注
    
    -- 若玩家在此节点问了AI，记录问答
    ai_qa_id        UUID                        -- 关联到qa_history
);
```

### 2.6 AI问答历史

```sql
CREATE TABLE qa_history (

    created_at      TIMESTAMP DEFAULT NOW()
);

### 3.1 Kimi API调用策略

**整体流程：**

```
用户上传截图
    ↓
┌────────────────────────────────────────┐
│ 步骤1：截图预处理                       │
│ • 压缩至合适尺寸（最大1920px长边）       │
│ • 格式转为 WebP/JPEG（减小体积）         │
│ • 提取/缓存 image_hash 去重              │
└────────────────────────────────────────┘
    ↓
┌────────────────────────────────────────┐
│ 步骤2：视觉识别（Kimi Vision API）        │
│ 请求Kimi vision模型识别图中元素：         │
│ • 当前角色                             │
│ • 手牌（名称、费用）                    │
│ • 能量值                               │
│ • 敌人名称、血量、意图                    │
│ • 当前场景（战斗/选牌/地图/事件）         │
└────────────────────────────────────────┘
    ↓
┌────────────────────────────────────────┐
│ 步骤3：数据增强（本地数据库查询）          │
│ 根据识别结果，查询本地数据库补充：         │
│ • 卡牌完整效果（含升级前后）              │
│ • 敌人意图详情、推荐策略                  │
│ • 当前角色流派知识                        │
│ • 相关遗物/药水效果                       │
└────────────────────────────────────────┘
    ↓
┌────────────────────────────────────────┐
│ 步骤4：策略生成（Kimi Chat API）          │
│ 构建结构化Prompt：                        │
│ • System Prompt：游戏规则+角色知识         │
│ • Context：当前对局状态（手牌、能量等）    │
│ • Question：用户具体问题                  │
│ • Constraints：必须用中文、分步骤解释       │
└────────────────────────────────────────┘
    ↓
┌────────────────────────────────────────┐
│ 步骤5：回答后处理                        │
│ • 事实核查（对比数据库中的卡牌效果）        │
│ • 添加免责声明（"仅供参考"）              │
│ • 缓存问答结果（相同截图+问题直接返回）     │
└────────────────────────────────────────┘
```

### 3.2 Prompt工程策略

**System Prompt模板（战斗建议场景）：**

```

### 3.3 API调用成本控制

| 场景 | 模型 | 估算Token | 单次成本（¥） |
|------|------|----------|-------------|
| 截图识别 | Kimi Vision | 输入~2K（含图） | ~¥0.05 |
| 策略生成 | Kimi Chat | 输入~3K + 输出~1K | ~¥0.03 |
| **合计单次问答** | - | - | **~¥0.08** |

**成本控制策略：**
1. **缓存机制**：相同image_hash + 相同question → 直接返回缓存结果
2. **预识别缓存**：截图中的卡牌组合先OCR识别，纯文字问题不走vision API
3. **限流**：匿名用户每日10次，登录用户每日50次，付费用户不限
4. **压缩策略**：图片压缩至800×600分辨率再上传，vision模型足够识别

**预估月成本（按活跃用户量）：**

| 活跃用户 | 日均问答/人 | 月API成本 |
|---------|-----------|----------|
| 500 | 3 | ~¥3,600 |
| 2,000 | 3 | ~¥14,400 |
| 5,000 | 3 | ~¥36,000 |

### 3.4 截图识别技术路径

**技术方案选择：**

| 方案 | 描述 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **A. 纯Vision LLM** | 直接让Kimi Vision识别图中所有元素 | 实现简单，通用性强 | 成本高、识别精度依赖模型 | MVP首选 |
| **B. Vision+规则后处理** | Vision粗识别 + 本地规则修正 | 精度提升、可兜底 | 开发量中等 | v0.2 |
| **C. 专用OCR+模板匹配** | PaddleOCR/TrOCR + 游戏UI模板匹配 | 精度最高、成本最低 | 需针对StS训练、维护成本高 | v1.0考虑 |

**MVP阶段推荐方案A**：
- 使用Kimi Vision API的`detail: "low"`模式（压缩图）降低成本
- 配合精心设计的Prompt引导模型准确识别游戏元素
- 在Prompt中提供StS界面布局说明（手牌在底部、敌人在上方等）

**Prompt中的视觉引导：**
```
这是《杀戮尖塔》游戏截图。请识别以下元素：
- 底部区域是玩家的手牌，每张牌显示费用（左上角数字）和名称
- 左下角显示当前能量（蓝色球）
- 上方是敌人，显示名称和血量
- 请用JSON格式输出识别结果...
```
