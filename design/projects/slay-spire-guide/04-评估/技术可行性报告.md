## 一、功能实现难度评估

### 1.1 P0功能评估

| 功能 | 实现难度 | 技术依赖 | 风险点 | 备注 |
|------|---------|---------|--------|------|
| **截图上传与存储** | **低** | 标准Web上传组件 | 无 | 拖拽/粘贴/选择文件，成熟方案 |
| **截图识别（Vision API）** | **中** | Kimi Vision API | API识别精度、成本 | MVP用Kimi Vision，fallback到文字输入 |
| **卡牌/遗物即时查询** | **低** | PostgreSQL + 全文检索 | 数据录入工作量 | 数据来自Wiki爬取+人工审核 |
| **卡牌数据库（两代兼容）** | **中** | 数据库设计 + 爬虫 | StS2数据不完整（EA中） | StS1数据完整可先行；StS2随版本迭代补充 |
| **敌人/BOSS数据库** | **中** | 同上 | 同上 | 敌人意图模式需结构化，录入工作量较大 |
| **对局截图记录** | **低** | 本地存储/数据库存储 | 存储空间增长 | 初期本地IndexedDB，后期迁移服务端 |
| **AI问答（战斗建议）** | **中** | Kimi Chat API + Prompt工程 | AI幻觉、时效性 | 核心差异化功能，需重点打磨Prompt |
| **AI问答（选牌建议）** | **中** | 同上 + 卡组识别 | 卡组识别精度 | 需从截图中提取当前卡组信息 |

### 1.2 P1功能评估

| 功能 | 实现难度 | 技术依赖 | 风险点 | 备注 |
|------|---------|---------|--------|------|
| **路线选择建议** | **中** | 地图识别 + 策略引擎 | 地图节点识别、策略模型 | 需识别地图上的节点类型和分布 |
| **卡组流派分析** | **中** | 卡组识别 + 流派匹配算法 | 流派定义主观性 | 规则匹配+LLM辅助，非纯算法 |
| **遗物组合推荐** | **低** | 规则引擎 | 无 | 基于已知协同关系的规则推荐 |
| **网络攻略自动同步** | **中** | 爬虫 + AI摘要 | 反爬、数据质量 | 详见技术架构中的爬虫方案 |
| **AI自动复盘** | **高** | 对局时间线 + 多节点AI分析 | 计算成本高、分析深度 | 需分析整局多个决策点，token消耗大 |

### 1.3 P2功能评估

| 功能 | 实现难度 | 技术依赖 | 风险点 | 备注 |
|------|---------|---------|--------|------|
| **联机模式策略** | **高** | 多人状态识别 + 协作策略 | StS2联机数据稀缺 | 需积累大量联机对局数据 |
| **数据统计看板** | **中** | 数据聚合 + 可视化 | 样本量不足（初期） | 用户数上去后才有统计意义 |

| **浏览器插件** | **中** | 浏览器扩展API | 审核、兼容性 | Chrome/Edge扩展开发 |
| **桌面端Electron** | **中** | Electron框架 | 包体积、更新机制 | P2阶段考虑 |

## 三、关键风险点

### 3.1 高风险

#### R1：AI幻觉导致错误策略建议

**描述**：LLM可能编造不存在的卡牌效果、错误的伤害计算、不合理的策略建议。这在策略游戏中后果严重——用户按错误建议操作导致死亡，会立即丧失信任。

**影响**：⭐⭐⭐⭐⭐（产品核心价值的毁灭性打击）

**概率**：中（Prompt工程不到位时高，到位后中）

**缓解措施**：
1. **事实核查层**：AI回答后，用本地数据库中的卡牌效果做后校验
2. **置信度标注**：对不确定的建议标注"仅供参考"或"建议再确认"
3. **Prompt约束**：严格限制AI只能使用提供的上下文数据，禁止"猜测"
4. **A/B测试**：不同Prompt版本对比幻觉率，持续优化
5. **用户反馈闭环**：用户可标记"回答有误"，人工审核后修正

#### R2：截图识别精度不足

**描述**：Kimi Vision或其他视觉模型可能无法准确识别StS游戏界面中的卡牌名称、费用、敌人意图等关键信息。

**影响**：⭐⭐⭐⭐（核心交互受阻）

**概率**：中（现代Vision模型对清晰UI识别能力较强，但StS2新卡牌可能不在训练数据中）

**缓解措施**：
1. **文字输入fallback**：截图识别失败时，允许用户手动输入手牌和状态
2. **Prompt引导**：在vision请求中详细描述StS界面布局，引导模型关注正确区域
3. **多模态结合**：截图 + 用户简短文字描述（如"战士第2层，打乐嘉"）
4. **逐步升级识别方案**：MVP用Vision LLM → v0.2加规则后处理 → v1.0考虑专用OCR

#### R3：StS2数据不完整且快速变动

**描述**：StS2处于Early Access阶段，卡牌数值、敌人机制、角色能力可能每版本变更。我们的数据库需要持续同步，否则攻略会误导用户。

**影响**：⭐⭐⭐⭐（产品可信度下降）

**概率**：高（EA游戏特性）

**缓解措施**：
1. **版本标记**：每条数据标注"适用版本"，过期数据明确提示"可能已变更"
2. **自动化同步**：爬虫每日扫描官方更新日志和Wiki变更
3. **社区众包**：允许用户提交"发现数据错误"，快速修正
4. **AI兜底**：当本地数据缺失时，让LLM基于最新知识回答（带免责声明）
5. **聚焦StS1先行**：StS1数据稳定完整，可先以StS1为主验证产品，StS2随版本成熟逐步深入

### 3.2 中风险

#### R4：API成本超预算

**描述**：若用户量增长快于预期，Kimi API调用费用可能超出初期预算。

**影响**：⭐⭐⭐（运营成本压力）

**缓解措施**：
1. 严格的缓存策略（相同截图+问题直接返回缓存）
2. 分级限流（匿名10次/日，登录50次/日，付费不限）
3. 图片压缩后再上传（降低vision token消耗）
4. 多模型fallback（高价值用户用Kimi，普通查询可用成本更低的模型）

#### R5：爬虫被目标网站封禁

**描述**：Fandom Wiki、Steam社区等可能限制或封禁我们的爬虫。

**影响**：⭐⭐⭐（数据同步受阻）

**缓解措施**：
1. 遵守robots.txt，使用官方MediaWiki API
2. 请求频率严格限制（每请求间隔≥2秒）
3. 声明User-Agent用途（社区服务，非商业竞争）
4. 准备备用数据源（多个Wiki镜像、社区备份）
5. 最坏情况：转为半人工同步（AI辅助提取 + 人工录入）

#### R6：用户量不及预期

**描述**：垂直游戏工具的用户天花板较低，可能无法达到PRD中预估的5000+活跃用户。

**影响**：⭐⭐⭐（产品可持续性）

**缓解措施**：
1. MVP阶段重点验证"用户是否真的会在游戏中使用"
2. 与B站UP主合作，将工具嵌入内容生态（UP主推荐引流）
3. 免费策略降低使用门槛（基础功能免费，高级功能可选付费）
4. 能力复用：截图识别+卡牌AI顾问的能力可扩展至Balatro、Hearthstone等游戏

### 3.3 低风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 浏览器兼容性问题 | 低 | 优先支持Chrome/Edge（覆盖90%+用户） |
| 存储空间不足 | 低 | 截图压缩、定期清理、用户可手动删除 |
| 竞品快速跟进 | 低 | 先发优势+社区壁垒+数据积累 |
| 法律风险（版权） | 低 | 仅引用公开数据，不使用游戏素材，注明数据来源 |

## 四、推荐MVP范围

### 4.1 必须包含（MVP v0.1）

| 功能 | 说明 | 为什么必须 |
|------|------|-----------|
| **截图AI问答** | 核心差异化功能 | 验证"AI实时建议"的假设，是产品存在的理由 |
| **卡牌数据库** | StS1完整 + StS2已确认数据 | 提供AI回答的事实基础，也是独立价值点 |
| **遗物数据库** | 同上 | 与卡牌同等重要的决策因素 |
| **敌人数据库** | StS1完整 + StS2已知BOSS | AI建议需要敌人数据支撑 |
| **基础搜索** | 卡牌/遗物名称搜索 | 最低门槛的查询功能 |
| **两代切换** | 一键切换StS1/StS2 | 验证市场假设：两代玩家是否都需要 |
| **对局记录** | 手动截图保存 + 时间线 | 为进阶用户提供价值，形成使用粘性 |

### 4.2 必须排除（MVP不做）

| 功能 | 排除原因 |
|------|---------|
| 联机策略建议 | StS2联机模式尚在早期，数据不足，且用户量少 |
| 自动爬虫同步 | 开发周期长，MVP阶段可手动更新StS2数据 |
| 数据统计看板 | 需要大量用户数据才有意义，MVP阶段无样本 |
| 浏览器插件 | 增加开发复杂度，先验证Web形态是否被接受 |
| 付费系统 | MVP免费，验证留存后再考虑 monetization |
| 内容创作辅助 | 面向UP主的功能，用户量小，P2再做 |

### 4.3 MVP成功标准

在MVP发布后4周内：
- [ ] 累计注册用户 ≥ 200
- [ ] 周活跃问答用户 ≥ 50
- [ ] 截图问答满意度 ≥ 70%
- [ ] 用户7日留存 ≥ 25%
- [ ] 无重大AI幻觉事故（无用户因错误建议投诉）

若达到以上标准，说明核心假设成立，可投入v0.2增强功能。
若未达标，需复盘：是AI建议质量不足？还是用户不习惯切屏使用？还是市场本身不够大？

## 五、技术可行性结论

### 5.1 总体评估

| 维度 | 评估 | 说明 |
|------|------|------|
| **技术可实现性** | ✅ **可行** | 所有P0功能均能用现有技术实现，无阻塞性技术难题 |
| **开发周期** | ⚠️ **可控但紧张** | MVP 8~10周，v1.0约3.5~4个月，需专人投入 |
| **成本控制** | ⚠️ **需关注API费用** | MVP阶段月成本¥3,000~5,000可接受，随用户增长线性上升 |
| **数据风险** | ⚠️ **StS2变动是主要不确定因素** | StS1数据稳定，StS2需持续跟进 |
| **AI质量** | ⚠️ **需要重点打磨** | 是产品成败的核心变量，需投入足够时间优化 |

### 5.2 是否推荐立项

**结论：✅ 推荐立项，进入MVP开发阶段。**

理由：
1. 技术路径清晰，无不可逾越的技术障碍
2. MVP周期可控（2~2.5个月），投入成本可接受
3. 即使StS2热度下降，积累的技术能力（截图识别+卡牌AI顾问）可复用至其他游戏
4. 市场空白明确，先发优势明显
5. 风险可控，最大风险（AI质量）可通过Prompt工程和事实核查层缓解

### 5.3 前提条件

立项前需确认：
1. **Irra技术预研**：用5~10张真实StS截图测试Kimi Vision识别精度，确认可行后再正式启动
2. **数据准备启动**：StS1卡牌/遗物/敌人数据的录入工作可并行开始（约1周工作量）
3. **Kimi API账号**：确认API额度充足，了解rate limit
