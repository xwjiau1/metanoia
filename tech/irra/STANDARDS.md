# Metanoia（启明科技）CTO技术部开发规范

**版本：** V1.0
**生效日期：** 2026-05-08
**适用范围：** 所有AI应用项目
**责任人：** CTO子agent（技术执行）+ wenner（主脑审核）

---

## 一、开发流程总览

```
PRD对接 → 开发方案+原型 → 方案确认 → 实际开发 → 回归测试 → 问题修复 → 构建打包 → 归档入库
```

**阶段数：** 8个标准阶段
**执行模式：** 主脑派单 → CTO执行 → 主脑审核 → CEO确认

---

## 二、各阶段规范

### Stage 1: PRD对接

**输入：** 产品需求文档（PRD）
**责任人：** wenner（主脑）
**动作：**
- 快速阅读PRD全文
- 识别P0（必须）/ P1（重要）/ P2（可选）优先级
- 确认MVP范围，砍掉非核心功能
- 输出：PRD摘要 + 功能优先级清单

**标准：**
- PRD必须包含：产品定位、功能模块、UI规范、技术约束
- 如无PRD，主脑需先引导CEO产出PRD后再进入下一阶段

---

### Stage 2: 开发方案 + 原型设计

**责任人：** CTO子agent
**交付物：**
1. `dev-plan.html` — 技术方案文档
   - 技术栈选型（轻量优先）
   - 数据库Schema设计
   - API接口定义
   - 开发排期（人天估算）
   - 风险分析（高/中/低分级）

2. `prototype.html` — 可交互原型
   - 浏览器可打开
   - 覆盖所有P0功能流程
   - 包含页面切换、表单、动画

**质量标准：**
- 技术方案必须与PRD约束一致
- 原型必须可交互，不能是静态截图
- 排期必须细化到周/日级别

---

### Stage 3: 方案确认

**责任人：** CEO（嘉文）
**动作：**
- 审查开发方案和原型
- 确认技术选型
- 确认MVP范围
- 给出"进入开发"指令

**标准：**
- CEO确认前不得进入Stage 4
- 如有修改意见，返回Stage 2重新调整

---

### Stage 4: 实际开发

**责任人：** CTO子agent
**输入：** 确认后的开发方案 + 原型
**交付：**
- 完整项目源代码
- `deployment-guide.html` — 配置上线手册
- `user-manual.html` — 产品使用说明书

**约束：**
- MVP优先：只做P0功能
- 轻量优先：避免过重依赖
- 代码质量：注释清晰，关键逻辑有说明
- 数据完整性：数据库Schema完整，预留扩展字段
- 离线可用：所有核心功能无需联网

**技术标准：**
- 代码文件按功能模块化（screens/ components/ database/ store/ utils/）
- 使用SQLite做本地持久化
- 深色模式UI（主色#E53935，背景#212121，强调#00C853）
- 大字体、大按钮、单手操作友好

---

### Stage 5: 回归测试

**责任人：** CTO子agent
**交付：**
- `test-cases.html` — 测试用例文档（至少30条）
- `test-report.html` — 测试报告

**测试范围（必须覆盖）：**
1. 功能测试：每个P0模块至少3条用例
2. UI/UX测试：深色模式、大字体可读性、按钮响应
3. 边界测试：空值、空状态、异常输入
4. 数据持久化测试：关闭重开后数据保留
5. 数据库Schema验证：表结构、外键、约束完整性
6. 代码审查：SQL注入风险、内存泄漏、未使用导入

**问题分级：**
- 严重：崩溃、数据丢失、功能完全失效 — 必须修复
- 高：核心功能异常、导航失效 — 必须修复
- 中：边界情况未处理、空状态缺失 — 建议修复
- 低：UI微调、提示文字优化 — MVP可延期

**标准：**
- 严重/高级问题必须清零才能进入Stage 6
- 测试用例数量 ≥ 30条

---

### Stage 6: 问题修复

**责任人：** CTO子agent
**动作：**
- 按优先级修复Stage 5发现的问题
- 修复后在源代码中直接修改
- 记录修复内容到测试报告

**约束：**
- 修复优先处理影响可用性的问题
- 不得引入新依赖或大幅重构
- 保持MVP轻量特性

---

### Stage 7: 构建打包

**责任人：** CTO子agent
**流程：**
1. 环境准备（Node.js + Expo CLI + EAS CLI）
2. 本地调试（Metro Bundler启动验证）
3. EAS云端构建（需Expo账号 + Access Token）
4. APK下载到服务器本地
5. 主脑审核后发送到CEO微信

**版本管理：**
- v1.0 — 初始构建（可能不含修复）
- v1.1 — 修复后重新构建（推荐交付版本）
- 后续迭代按v1.2, v1.3递增

**注意：**
- 服务器无Android SDK，必须使用EAS云端构建
- 构建排队时间通常10-20分钟
- Access Token需CEO提供（github.com/settings/tokens）

---

### Stage 8: 归档入库

**责任人：** CTO子agent + wenner（主脑）
**核心要求：代码必须推送到GitHub才算任务完成。**

**工作目录标准结构：**

```
projects/{project-name}/
├── 01-PRD/                    # 产品需求文档
├── 02-设计/                   # 开发方案 + 原型
├── 03-源码/                   # 完整项目代码（含.git）
├── 04-文档/                   # 上线手册 + 产品说明书
├── 05-测试/                   # 测试用例 + 测试报告
├── 06-构建/                   # APK构建产物
├── 07-过程/                   # 构建日志 + 流程总结
└── README.md                  # 项目总览
```

**GitHub推送规范（强制执行）：**
- **前置条件：** 所有代码已提交到本地git，README和LICENSE已就位
- **推送方式：** 使用技术部专用skill `metanoia-github-push`
  - 脚本位置：`~/.openclaw/workspace/skills/metanoia-github-push/scripts/github-push.sh`
  - 一键推送：`bash ~/.openclaw/workspace/skills/metanoia-github-push/scripts/github-push.sh [项目路径] [仓库名]`
- 仓库命名：小写连字符（如 `spireguide`）
- 公开仓库（展示用）
- 提交记录清晰：
  - `feat:` 新功能
  - `fix:` 修复
  - `docs:` 文档
  - `chore:` 构建/配置
- 不推送构建产物（APK/dist等二进制文件，通过.gitignore排除）
- 必须包含README.md、LICENSE和完整过程文档

**推送失败时的处理：**
1. 检查token是否过期（`curl -H "Authorization: token ..." https://api.github.com/user`）
2. 检查仓库是否已存在（通过API创建或确认）
3. 重试推送
4. 仍失败 → 向wenner汇报阻塞原因

**交付完成标准（CTO必须自检）：**
| # | 检查项 | 验证命令 |
|---|--------|----------|
| 1 | Git提交历史完整 | `git log --oneline` |
| 2 | 远程仓库已配置 | `git remote -v` |
| 3 | GitHub可访问 | 浏览器打开 `github.com/xwjiau1/REPO_NAME` |
| 4 | README已就位 | `ls README.md` |
| 5 | LICENSE已就位 | `ls LICENSE` |

**不满足以上5项 = 任务未完成，不得进入下一阶段。**

```bash

```

## 七、心流模式（Flow Mode）

**定义：** 针对单一项目的持续循环迭代工作流。CTO技术部进入自动循环状态，完成一版→测试→交付→自动进入下一版，直到最终版本或CEO主动叫停。

**适用场景：**
- 已有明确迭代路线图（如HYROS Fit的v1.2→v2.0→v2.5→v3.0）
- CEO希望"全自动推进"，减少每次版本都需要人工确认
- 项目处于密集开发期，需要持续产出

---

### 7.1 心流循环流程

```
┌─────────────────────────────────────────────────────────────┐
│                         心流循环                              │
│                                                             │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐  │
│  │ 版本开发 │ → │ 回归测试 │ → │ 构建打包 │ → │ CEO验证 │  │
│  └──────────┘   └──────────┘   └──────────┘   └──────────┘  │
│       ↑                                              │      │
│       └────────────── 通过 ──────────────────────────┘      │
│                      不通过 → 返回修复                        │
│                                                             │
│  循环条件：未达到最终版本 且 CEO未叫停                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**单次循环内的8个阶段（继承标准流程）：**

| 阶段 | 动作 | 责任人 | 交付物 |
|------|------|--------|--------|
| 1. 需求对齐 | wenner根据迭代路线图提取当前版本功能清单 | wenner | 版本任务书 |
| 2. 技术方案 | 如有架构变更，出delta方案 | CTO | 技术方案（如有） |
| 3. 开发 | 按功能清单编码 | CTO | 源码 |
| 4. 测试 | 回归测试 + 新功能测试 | CTO | 测试报告 |
| 5. 修复 | 修复测试发现的问题 | CTO | 修复后代码 |
| 6. 构建 | EAS云端打包APK | CTO | APK文件 |
| 7. 交付 | wenner审核后发给CEO | wenner | APK + 报告 |
| 8. 验证 | CEO真机测试，确认/打回 | CEO | 通过 → 进入下一循环 |

---

### 7.2 自动推进规则

**进入下一循环的条件（同时满足）：**
1. 上一版本代码完成+Git推送
2. 未达到路线图最终版本
3. CEO未发送"停止""暂停""心流停止"

**注意：不需要CEO逐版确认。完成即推进，叫停才暂停。**

**暂停循环的条件（任一满足）：**
1. CEO发送"停止""暂停""心流停止"
2. 测试发现严重/高问题未清零（必须修复后才能继续）
3. EAS构建失败且无法自动恢复
4. CTO执行异常（宕机/超时/错误）

**版本号递增规则：**
- Hotfix：vX.Y → vX.Y+1（如v1.1→v1.2）
- 功能迭代：vX.Y → vX+1.0（如v1.2→v2.0）
- 每次心流循环产出至少一个可安装的APK

---

### 7.3 监工机制（持续监控）

**心流模式必须伴随持续监工。**

**监工启动时机：**
- 每次CTO新任务spawn时，wenner注册监工到管理器
- `bash /tmp/flow-monitor-manager.sh register <任务ID> <工作目录> <完成检查命令>`
- 任务ID格式：`{项目代号}-{阶段号}`（如 STS-DEV-001）

**监工关闭时机：**
- CTO任务完成且wenner确认后，注销监工
- `bash /tmp/flow-monitor-manager.sh complete <任务ID>`
- 注销后清理该任务的临时状态文件

**监控内容：**
1. 检查CTO工作目录文件变化（排除node_modules/.git）
2. 10分钟无产出变化 → 发送警告到CEO微信
3. 检测到关键交付物 → 发送进度更新
4. 完成条件满足 → 发送完成通知

**监工脚本位置：** `/root/.openclaw/workspace/monitor-cto.sh`
**监控频率：** 每10分钟
**推送渠道：** CEO微信（openclaw-weixin）

---

### 7.4 异常熔断机制

| 异常场景 | 熔断动作 | 通知 |
|----------|----------|------|
| CTO执行超过40分钟无产出 | kill当前CTO，重新spawn | 立即推送CEO |
| 同一版本连续2次构建失败 | 暂停心流，人工排查 | 立即推送CEO |
| 测试发现≥2个严重问题 | 暂停心流，等待修复确认 | 立即推送CEO |
| CEO未回复验证超过24h | wenner主动提醒一次，48h后自动暂停 | 提醒推送 |
| 服务器磁盘空间<1GB | 暂停心流，清理空间 | 立即推送CEO |

---

### 7.5 心流模式启动/停止指令

**CEO指令集：**

| 指令 | 效果 |
|------|------|
| "开启心流" / "心流模式" / "开始循环" | 启动心流循环，从当前版本开始自动推进 |
| "心流停止" / "暂停心流" / "停止循环" | 当前循环完成后暂停，不再自动进入下一版 |
| "紧急停止" / "立刻停止" | 立即kill当前CTO，关闭监控，完全停止 |
| "继续" / "通过" / "下一版" | 当前版本验证通过，进入下一循环 |
| "打回" / "重做" / "修复" | 当前版本不通过，返回Stage 6修复 |

---

### 7.6 心流模式下的CTO任务派发规范

**每次循环的任务书格式：**

```
【任务编号】HYROS-{版本号}
【任务来源】wenner心流自动派发
【版本目标】v{X.Y}
【功能清单】
  1. FE-XXX: {功能名}
  2. FE-XXX: {功能名}
  ...
【修复清单】（如为修复版本）
  1. FIX-XXX: {问题描述}
  ...
【约束】
  - 基于上一版本代码（projects/hyros-fit/03-源码/）
  - 不得破坏已有功能
  - 数据库Schema变更需兼容旧数据
  - 构建后必须生成APK
【完成汇报】
  1. 实现的功能清单
  2. 测试用例数量及结果
  3. APK文件路径
  4. 已知限制
  5. 下一版本建议
```
