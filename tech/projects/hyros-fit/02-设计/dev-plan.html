1 项目概述

1.1 产品定位

名称: HYROS Fit

Slogan: 计划即执行，打卡即进步

定位: 面向有结构化训练计划的进阶健身者的计划管理 + 执行工具

核心价值: AI计划导入 + 日历打卡 + 数据看板，三位一体化

1.2 目标用户

维度主要用户 (结构化训练者)次要用户 (计划制定者)
年龄20-35岁25-40岁
性别男性70% / 女性30%均衡
经验6个月以上，有明确分化计划专业教练/博主
频率每周4-6次为客户制定
设备安卓为主，部分iOS多端
场景健身房实时打卡，训练后看统计计划分发

1.3 竞品分析

产品优势劣势HYROS差异化
Keep内容丰富，用户基数大缺乏进阶计划管理结构化计划 + 进阶追踪

3 技术栈选型

3.1 前端框架: React Native

DECISION

选择: React Native (Expo)

理由:

  • 目标用户以安卓为主，React Native一套代码覆盖Android + iOS，降低维护成本
  • Expo生态成熟，提供Expo Calendar、Expo Notifications等模块，减少原生开发
  • 社区庞大，第三方库丰富 (如react-native-draggable-flatlist用于拖拽排序)
  • 热更新支持 (Expo OTA)，便于快速迭代修复
  • 团队学习曲线较Flutter平缓，JavaScript/React生态人才充足

备选: Flutter — 性能更优，UI一致性更好，但Dart生态相对较小，复杂动画实现成本高。若团队有Flutter经验可切换。

3.2 状态管理: Zustand + React Query

DECISION

选择: Zustand (客户端状态) + React Query (服务端状态)

  • Zustand: 极简API，无样板代码，适合训练打卡等局部状态
  • React Query: 内置缓存、乐观更新、离线支持，完美契合健身App的数据同步场景
  • 组合使用避免Redux的过度工程化

3.3 本地数据库: SQLite + Drizzle ORM

DECISION

选择: SQLite (expo-sqlite) + Drizzle ORM

  • SQLite: 成熟可靠，Expo内置支持，零配置
  • Drizzle ORM: 类型安全，轻量，SQL-like语法直观，支持迁移
  • 备选: TypeORM 较重；Prisma 不支持React Native。Drizzle为最优解
  • 数据加密: SQLCipher 封装，保护用户训练数据

3.4 后端方案: Supabase (推荐)

DECISION

选择: Supabase (BaaS)

维度SupabaseFirebase自建Node.js
成本 (初创)免费档够用免费档够用需服务器成本
数据库PostgreSQL (关系型，适合结构化健身数据)Firestore (文档型)PostgreSQL/MySQL
实时同步原生支持 (WebSocket)原生支持需自建WebSocket
认证内置 (手机/邮箱/第三方)内置需自建
存储S3兼容对象存储Cloud Storage需自建
边缘函数Edge Functions (Deno)Cloud Functions需自建
数据锁定可导出，无锁定深度绑定完全自主
AI扩展pgvector向量存储 (未来AI功能)Vertex AI需自建

决策理由:

  • 健身数据高度结构化 (计划/训练日/动作/组/记录)，PostgreSQL的关系模型天然适配
  • Supabase提供实时订阅，训练数据多端同步无需自建WebSocket
  • 初创阶段零服务器成本，按需付费
  • 未来AI功能 (动作推荐/计划生成) 可直接使用pgvector

自建Node.js备选: 若用户量突破10万或需深度定制AI逻辑，可迁移至自建后端 + Supabase作为数据库层。

3.5 AI/NLP方案: 规则引擎 + LLM备用

DECISION

选择: 自研规则引擎 (主) + 云端LLM API (备用)

方案适用阶段成本准确率
规则引擎 (正则 + 分词)MVP (文本导入)零API成本85%+ (结构化文本)
云端LLM (GPT-4o-mini / Claude Haiku)P1+ (复杂文本/截图)~$0.01/次95%+
端侧OCR (ML Kit)P2 (截图识别)零成本依赖图片质量

策略:

  • Phase 1 (MVP): 纯规则引擎处理文本粘贴导入。健身计划文本格式相对固定，规则引擎足以覆盖大多数场景
  • Phase 2: 接入云端LLM作为高置信度备份。规则引擎失败时自动降级到LLM
  • Phase 3: 引入端侧OCR (Google ML Kit) 处理截图/拍照
  • 长期: 基于用户修正数据微调小型模型，提升特定用户群体的识别准确率

3.6 离线同步策略

DECISION

策略: 本地优先 (Local-First) 架构

┌─────────────────────────────────────────┐
│              用户操作                     │
│         (打卡/输入/编辑)                   │
└──────────────┬──────────────────────────┘
               │ 1. 立即写入本地SQLite
               ▼
┌─────────────────────────────────────────┐
│           本地SQLite数据库                 │
│      (主数据源，始终可用)                  │
└──────────────┬──────────────────────────┘
               │ 2. 同步队列 (Pending)
               ▼
┌─────────────────────────────────────────┐
│           同步引擎                         │
│  - 检测网络状态                           │
│  - 批量同步 (debounce 5s)                 │
│  - 冲突解决 (Last-Write-Wins + 手动合并)   │
│  - 离线队列持久化                         │
└──────────────┬──────────────────────────┘
               │ 3. 网络可用时同步
               ▼
┌─────────────────────────────────────────┐
│         Supabase (云端)                    │
│    PostgreSQL + Realtime订阅              │
└─────────────────────────────────────────┘

关键规则:

  • 所有写操作先写本地，再异步同步云端
  • 同步队列持久化到SQLite，App崩溃/杀进程不丢失
  • 批量同步间隔: 5秒防抖，减少API调用
  • 冲突解决: 同一记录冲突采用时间戳优先 (LWW)，训练数据冲突提示用户手动选择
  • 首次登录: 全量拉取云端数据覆盖本地
  • 定期全量校验: 每周一次完整数据哈希比对

6 核心算法/逻辑

6.1 NLP解析规则 (文本导入)

输入示例: 平板杠铃卧推 4组x8-10次 休息90s

解析流水线

输入文本
  │
  ▼
┌─────────────────────────────────────────┐
│ Step 1: 预处理                           │
│  - 统一全角/半角                          │
│  - 去除多余空格                           │
│  - 识别日期行 ("周一" / "Day 1")         │

// 动作名模糊匹配
function fuzzyMatchExercise(input: string, exerciseList: Exercise[]): MatchResult {
  // 1. 精确匹配
  const exact = exerciseList.find(e => 
    e.name_cn === input || 
    e.name_en === input ||
    e.aliases?.includes(input)
  );
  if (exact) return { exercise: exact, confidence: 1.0 };
  
  // 2. 包含匹配
  const contains = exerciseList.find(e => 
    e.name_cn.includes(input) || input.includes(e.name_cn)
  );
  if (contains) return { exercise: contains, confidence: 0.9 };
  
  // 3. Levenshtein 编辑距离
  const candidates = exerciseList.map(e => ({
    exercise: e,
    distance: levenshtein(input, e.name_cn),
    maxLen: Math.max(input.length, e.name_cn.length)
  }));
  
  const best = candidates
    .map(c => ({ ...c, confidence: 1 - c.distance / c.maxLen }))
    .sort((a, b) => b.confidence - a.confidence)[0];
  
  return best.confidence > 0.6 ? best : null;
}

function calculateSessionVolume(sets: WorkoutSet[]): number {
  return sets.reduce((total, set) => {
    if (set.is_completed && !set.is_skipped) {
      const volume = (set.weight_kg || 0) * (set.reps || 0);
      return total + volume;

    return total;
  }, 0);

// 周期容量趋势 (用于数据看板)
function calculateWeeklyVolume(
  sessions: WorkoutSession[],
  startDate: Date,
  endDate: Date
): { week: string; volume: number }[] {
  const weekly = groupByWeek(sessions, startDate, endDate);
  return weekly.map(week => ({
    week: week.label,
    volume: week.sessions.reduce(
      (sum, s) => sum + (s.total_volume_kg || 0), 0
    )
  }));
}

// 部位容量分布
function calculateBodyPartDistribution(
  sessions: WorkoutSession[],
  exercises: Exercise[]
): { category: string; volume: number; pct: number }[] {
  const byCategory: Record = {};
  let total = 0;
  
  sessions.forEach(session => {
    session.sets.forEach(set => {
      const exercise = exercises.find(e => e.id === set.exercise_id);
      const category = exercise?.category || '未知';
      const volume = (set.weight_kg || 0) * (set.reps || 0);
      byCategory[category] = (byCategory[category] || 0) + volume;
      total += volume;
    });
  });
  
  return Object.entries(byCategory)
    .map(([category, volume]) => ({
      category,
      volume,
      pct: total > 0 ? Math.round((volume / total) * 100) : 0
    }))
    .sort((a, b) => b.volume - a.volume);
}

6.3 连续打卡检测

// 连续打卡天数计算 (支持补签)
function calculateStreak(
  sessions: WorkoutSession[],
  today: Date = new Date()
): { currentStreak: number; longestStreak: number } {
  // 1. 获取所有有训练或补签的日期 (去重，按天)
  const activeDates = new Set(
    sessions
      .filter(s => s.status === 'completed' || s.is_backfill)
      .map(s => formatDate(s.actual_date || s.scheduled_date))
  );
  
  // 2. 获取所有休息日的日期
  const restDates = new Set(
    sessions
      .filter(s => s.status === 'rest_day')
      .map(s => formatDate(s.scheduled_date))
  );
  
  // 3. 当前连续打卡
  let currentStreak = 0;
  let checkDate = new Date(today);
  
  while (true) {
    const dateStr = formatDate(checkDate);
    
    if (activeDates.has(dateStr)) {
      currentStreak++;
      checkDate = addDays(checkDate, -1);
    } else if (isWeekend(checkDate) && restDates.has(dateStr)) {
      // 周末休息日不中断连续打卡 (可选策略)
      checkDate = addDays(checkDate, -1);
    } else if (isFuture(checkDate, today)) {
      // 未来日期跳过
      checkDate = addDays(checkDate, -1);
    } else {
      break;
    }
  }
  
  // 4. 历史最长连续
  const sortedDates = Array.from(activeDates).sort();
  let longestStreak = 0;
  let tempStreak = 1;
  
  for (let i = 1; i < sortedDates.length; i++) {
    const prev = parseDate(sortedDates[i - 1]);
    const curr = parseDate(sortedDates[i]);
    const diffDays = daysBetween(prev, curr);
    
    if (diffDays === 1) {
      tempStreak++;
    } else if (diffDays === 2 && isWeekend(curr)) {
      // 周末休息日不中断
      tempStreak++;
    } else {
      longestStreak = Math.max(longestStreak, tempStreak);
      tempStreak = 1;
    }
  }
  longestStreak = Math.max(longestStreak, tempStreak);
  
  return { currentStreak, longestStreak };
}

6.4 PR检测逻辑

// PR类型定义
type PRType = 'weight' | 'reps' | 'volume' | 'estimated_1rm';

// 1RM估算 (Epley公式)
function estimate1RM(weightKg: number, reps: number): number {
  if (reps === 1) return weightKg;
  return weightKg * (1 + reps / 30);
}

// PR检测主函数
function detectPersonalRecords(
  newSet: WorkoutSet,
  exerciseId: string,
  userId: string,
  historicalPRs: PersonalRecord[]
): { isPR: boolean; prType: PRType; previous?: PersonalRecord } {
  
  const weight = newSet.weight_kg || 0;
  const reps = newSet.reps || 0;
  const volume = weight * reps;
  const estimated1RM = estimate1RM(weight, reps);
  
  // 获取该动作的历史PR
  const exercisePRs = historicalPRs.filter(pr => pr.exercise_id === exerciseId);
  
  const checks: { type: PRType; value: number }[] = [
    { type: 'weight', value: weight },
    { type: 'reps', value: reps },
    { type: 'volume', value: volume },
    { type: 'estimated_1rm', value: estimated1RM }
  ];
  
  for (const check of checks) {
    const typePRs = exercisePRs.filter(pr => pr.record_type === check.type);
    const bestPR = typePRs.length > 0 
      ? typePRs.reduce((max, pr) => {
          const val = pr[check.type === 'weight' ? 'weight_kg' : 
                       check.type === 'reps' ? 'reps' : 
                       check.type === 'volume' ? 'volume_kg' : 'estimated_1rm'] || 0;
          return val > (max ? max.weight_kg || 0 : 0) ? pr : max;
        }, null as PersonalRecord | null)
      : null;
    
    const bestValue = bestPR 
      ? (check.type === 'weight' ? bestPR.weight_kg :
         check.type === 'reps' ? bestPR.reps :
         check.type === 'volume' ? bestPR.volume_kg :
         bestPR.estimated_1rm) || 0
      : 0;
    
    if (check.value > bestValue) {
      return { isPR: true, prType: check.type, previous: bestPR || undefined };
    }
  }
  
  return { isPR: false, prType: 'weight' };
}

// 简化版PR检测 (训练中使用，只检测重量和次数)
function quickPRCheck(
  newSet: { weight_kg: number; reps: number },
  exerciseHistory: { weight_kg: number; reps: number }[]
): { isPR: boolean; prType?: string; improvement?: string } {
  const maxWeight = Math.max(...exerciseHistory.map(h => h.weight_kg), 0);
  const maxRepsAtWeight = exerciseHistory
    .filter(h => h.weight_kg === newSet.weight_kg)
    .map(h => h.reps);
  const bestRepsAtWeight = Math.max(...maxRepsAtWeight, 0);
  
  if (newSet.weight_kg > maxWeight) {
    return { 
      isPR: true, 
      prType: '重量PR', 
      improvement: `+${(newSet.weight_kg - maxWeight).toFixed(1)}kg` 
    };
  }
  
  if (newSet.weight_kg === maxWeight && newSet.reps > bestRepsAtWeight) {
    return { 
      isPR: true, 
      prType: '次数PR', 
      improvement: `+${newSet.reps - bestRepsAtWeight}次` 
    };
  }
  
  return { isPR: false };
}

9 风险点与应对方案

高风险

训练打卡页面性能 (列表卡顿/输入延迟)

训练页面需要同时渲染多个动作的多个组，包含大量输入框和计时器。在低端安卓设备上可能出现明显卡顿。

应对:

  • 使用 FlatList + getItemLayout 优化长列表
  • 组输入使用受控组件 + debounce，避免每次输入都重渲染整个列表
  • 使用 React.memo + useMemo 隔离子组件重渲染
  • 考虑虚拟化: 只渲染可见区域内的组
  • Week 5 预留1天专门做性能测试和优化
高风险

离线同步数据冲突/丢失

用户可能在多设备/弱网环境下操作，数据冲突和同步延迟会导致训练记录丢失或覆盖。

应对:

  • 本地始终为主数据源，云端为备份
  • 实现操作日志 (Operation Log) 模式，记录每次修改的操作类型和目标
  • 冲突时优先保留用户最新操作，同时备份冲突数据供人工恢复
  • 全量数据哈希校验，每周自动比对
  • 提供"导出备份"功能，用户可手动导出SQLite文件
高风险

组间计时器后台保活

训练时用户可能锁屏或切换到其他App，计时器需要在后台持续运行并在结束时提醒。

应对:

  • 使用 expo-background-timer 实现后台计时
  • 结合 expo-notifications 在计时结束时发送本地通知
  • 记录计时开始时间戳，App回到前台时计算已流逝时间 (防杀后台)
  • Android: 使用前台服务 (Foreground Service) 提高保活率
  • iOS: 依赖后台任务API (BackgroundFetch)，限制较多
中风险

AI文本导入准确率不足

规则引擎对非标准格式、混合语言、手写笔记等场景识别率可能低于预期。

应对:

  • MVP阶段明确标注为"Beta功能"，管理用户预期
  • 提供丰富的示例文本引导用户粘贴标准格式
  • 未识别项高亮显示，一键手动修正
  • 收集用户修正数据，为后续LLM微调积累语料
  • Phase 2接入LLM作为高置信度备选
中风险

图表库在React Native中的兼容性

数据看板需要多种图表类型，部分React Native图表库在安卓上表现不稳定。

应对:

  • 优先选择纯JS实现的图表库 (react-native-gifted-charts)
  • 备选: 使用 WebView + ECharts 封装
  • 复杂图表降级为纯CSS实现 (如热力图)
  • Week 6 预留时间做图表兼容性测试
中风险

Supabase免费档容量/并发限制

Supabase免费档有数据库大小和并发连接限制，用户量增长后可能触发限制。

应对:

  • 设计阶段控制单用户数据量 (训练记录保留2年，过期归档)
  • 图片/文件使用Supabase Storage，不存数据库
  • 监控数据库大小，设定告警阈值
  • 预留迁移方案: 数据可导出，架构与自建PostgreSQL兼容
  • 用户量接近限制时平滑升级至Pro档 ($25/月)
低风险

React Native升级兼容性

Expo SDK 或 React Native 大版本升级可能引入破坏性变更。

应对:

  • 锁定版本，MVP阶段不主动升级大版本
  • 使用 Expo 托管工作流，减少原生依赖
  • 核心逻辑与框架解耦，便于迁移
低风险

应用商店审核延迟

首次上架App Store和Google Play可能审核不通过或延迟。

应对:

  • MVP阶段优先使用 Expo EAS 发布，简化流程
  • 提前准备隐私政策、用户协议
  • iOS TestFlight / Google Play Internal Testing 先行
